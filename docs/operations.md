# Эксплуатация и клиентский пилот

Этот документ описывает локальную синтетическую демонстрацию и подготовку отдельного экземпляра для клиента. Он не подтверждает настройку live-интеграций, публичной инфраструктуры или соблюдение конкретных правовых требований.

## Каталоги, доступы и процессы

| Назначение | Место |
|---|---|
| Локальные параметры приложения | `.env`, исключён из Git |
| Параметры отдельного Compose demo | `.env.compose`, исключён из Git |
| Пароль demo-оператора приложения | `%LOCALAPPDATA%\AILeadAutomationPro\demo-operator.json` |
| Пароль owner отдельного n8n | `%LOCALAPPDATA%\AILeadAutomationPro\n8n-demo\owner-access.json` |
| Ключ шифрования credentials n8n | `%LOCALAPPDATA%\AILeadAutomationPro\n8n-demo\encryption-key` |
| Кластер PostgreSQL | `%LOCALAPPDATA%\AILeadAutomationPro\postgres-17-demo-test\data` |
| Журналы PostgreSQL | `%LOCALAPPDATA%\AILeadAutomationPro\postgres-17-demo-test\postgres.log` |
| Данные/журналы отдельного n8n | `%LOCALAPPDATA%\AILeadAutomationPro\n8n-demo` |
| API/UI/worker журналы и PID-маркеры | `.local/` |
| Проверочные backups | `%LOCALAPPDATA%\AILeadAutomationPro\backups` |

Пароли и ключи не включаются в сообщения, screenshots, export workflows и обычные логи. Локальные файлы доступа предназначены владельцу этой Windows-учётной записи; перед клиентским пилотом секреты переносятся в согласованное защищённое хранилище с доступом только необходимых процессов.

Общий запуск: `scripts/start-dev.ps1`. Он проверяет доступность портов и не завершает чужие процессы. API считается готовым после HTTP 200 от `/health/ready`, UI — после HTTP 200; уже записанный, но ещё загружающийся процесс ожидается до 30 секунд без создания второй копии. Запуск, перезапуск API и остановка используют общий локальный lock. `scripts/stop-dev.ps1` останавливает только записанные API/UI/worker вместе с проверенными дочерними Python, Vite/esbuild и console-процессами; n8n и PostgreSQL останавливаются отдельными скриптами. После изменения `.env` перезапускаются API и worker. Изменение служебных токенов требует также остановки n8n и повторного `start-n8n.ps1 -Setup`.

В Windows-демонстрации PostgreSQL использует `trust` только на loopback и только для отдельных demo/test/n8n ролей. Это конфигурация для синтетических данных на одном компьютере. Для live она непригодна.

## Диагностика

| Симптом | Проверка и действие |
|---|---|
| Форма сообщает о сетевой ошибке | Проверить `/health/ready`, затем PostgreSQL. Повтор формы сохраняет исходный Idempotency-Key; новый ключ означает новое обращение |
| Заявка принята, но ждёт обработки | Проверить запущенный worker и `node n8n/manage-local.mjs verify`. Приём заявки не зависит от доступности n8n |
| n8n отвечает 404 на webhook | Проверить production path, publication status и четыре activated triggers; не использовать test webhook |
| n8n отвечает 403 | Проверить пару `N8N_WEBHOOK_TOKEN` приложения и соответствующий credential нового n8n, без публикации значения |
| Внутренний API отвечает 401/403 | Проверить `X-Internal-Token`, credentials n8n и `.env`; пользовательская сессия не заменяет служебный токен |
| `delivery_unknown` | Остановить повторные отправки этой версии; сверить Sent/провайдера по Message-ID. Не менять состояние прямо в БД ради повторного письма |
| Follow-up требует проверки | Проверить свежесть IMAP sync, несопоставленную почту и остановку коммуникации; отсутствие сохранённого ответа не доказывает отсутствие письма в недоступном ящике |
| n8n стартует, но часть triggers failed | Startup helper проверяет статусы и ограниченно восстанавливает публикацию уже опубликованной версии. Проверить PostgreSQL pool и журналы; публикация версии ещё не равна успешной активации |
| Порт занят | Определить владельца процесса. Скрипты не изменяют чужой экземпляр; согласовать свободный порт и связанные адреса |

HTTP readiness подтверждает готовность соответствующего процесса, а не работу всех внешних провайдеров. При проверке всегда сопоставлять состояние в PostgreSQL, шаги задания и историю заявки. Наличие зелёного health endpoint не доказывает доставку email.

## Резервное копирование и восстановление

Проверка синтетического приложения:

```powershell
.\.venv\Scripts\python.exe scripts/check-restore.py
```

Скрипт создаёт `pg_dump -Fc`, восстанавливает его **в новую случайно названную БД**, проверяет миграцию и отсутствие ссылок заданий на несуществующие заявки. Затем удаляет только собственную временную БД. Исходная `ai_leads_demo` остаётся нетронутой, проверочная копия сохраняется. Фактический результат каждого запуска указан в отчёте проверки. Скрипт не проверяет восстановление n8n, не шифрует архив и не устанавливает расписание.

Для полной локальной demo-копии нужно сохранить обе рабочие БД и ключ n8n. Выполнить в окно обслуживания, сначала остановив worker/API и project n8n, оставив PostgreSQL запущенным:

```powershell
.\scripts\stop-dev.ps1
.\scripts\stop-n8n.ps1
$backupStamp = (Get-Date).ToUniversalTime().ToString('yyyyMMdd-HHmmss')
$backupFolder = Join-Path $env:LOCALAPPDATA "AILeadAutomationPro\backups\$backupStamp"
New-Item -ItemType Directory -Path $backupFolder
$postgresTools = Join-Path (Get-Location) '.local\postgresql-17.11-4\pgsql\bin'
& (Join-Path $postgresTools 'pg_dump.exe') -h 127.0.0.1 -p 15432 -U ai_leads_demo -d ai_leads_demo -Fc -f (Join-Path $backupFolder 'app.dump')
& (Join-Path $postgresTools 'pg_dump.exe') -h 127.0.0.1 -p 15432 -U ai_leads_n8n -d ai_leads_n8n -Fc -f (Join-Path $backupFolder 'n8n.dump')
Copy-Item -LiteralPath (Join-Path $env:LOCALAPPDATA 'AILeadAutomationPro\n8n-demo\encryption-key') -Destination (Join-Path $backupFolder 'n8n-encryption-key')
.\scripts\start-dev.ps1
```

Проверять exit code каждой команды; неполный backup не считать пригодным. Эти архивы содержат синтетические данные и секреты n8n в зашифрованном виде, а отдельный encryption key раскрывает их при совместном доступе. Для клиента назначить отдельное зашифрованное хранилище, раздельный доступ к ключам и копиям, ежедневный backup и согласованный срок жизни — первоначально 30 дней. Автоматическое истечение/ротация в текущем локальном скрипте **не реализованы**.

Порядок восстановления клиента:

1. Создать изолированное пустое окружение с той же проверенной версией PostgreSQL и приложения; входящие запросы и внешние отправки оставить выключенными.
2. Восстановить прикладную БД через `pg_restore --no-owner --exit-on-error` с назначением корректного владельца. Проверить миграцию, количество сущностей, связи, состояния sending/delivery_unknown и незавершённые задания.
3. Отдельно восстановить БД n8n и её исходный encryption key. Проверить credentials и актуальные адреса backend. Не импортировать demo-секреты в live.
4. Повторно применить согласованные удаления, которые произошли после даты backup, и проверить список запрета коммуникации.
5. Проверить workflows и входящую синхронизацию. Только после проверки оператором открывать приём и запускать worker. Не возобновлять неопределённые SMTP-отправки автоматически.

RPO/RTO определяются клиентом по фактически испытанному процессу. Локальный restore smoke не доказывает восстановление всего клиентского окружения после аварии.

## Большое или неполностью проверенное входящее письмо

При размере больше 2 000 000 байт приложение не загружает полное содержимое.
Неоднозначный размер или несоответствие полученного тела также создают проблему
в существующем разделе «Входящие без связи с заявкой». Карточка содержит служебный
код, UIDVALIDITY, UID и размер; оригинальный текст туда не копируется. Курсор
продвигается только в одной транзакции с этой записью, поэтому следующие письма
продолжают обрабатываться без молчаливой потери проблемы.

Пока такая запись не разобрана, состояние IMAP — `needs_review`, а follow-up
всего единственного ящика заблокирован. Уже подготовленные повторные письма
также требуют ручной проверки; новая синхронизация сама их не разрешает.

Оператор проверяет оригинал в почтовом ящике и использует существующее ручное
сопоставление только при достоверной связи с заявкой. Указанная заявка получает
состояние ответа клиента, её follow-up отменяется. После разбора всех проблем
нужна свежая успешная синхронизация; для других затронутых заявок требуется
существующая ручная проверка follow-up и новое одобрение версии.

Если связь установить нельзя (в том числе для предположительно постороннего
письма), запись остаётся неразобранной и блокировка сохраняется. Нельзя привязать
её к случайной заявке ради снятия блока. Отдельный механизм игнорирования или
карантина не добавлен. Эта консервативная граница должна быть понятна оператору.

SMTP повторяется только после достоверного временного отказа до принятия.
Неоднозначный результат, в том числе некорректная структура отказа получателя,
остаётся `delivery_unknown` и требует сверки, а не повторной отправки.

## Хранение и удаление

Подробная процедура: [data-retention.md](data-retention.md). Начальные сроки для согласования: закрытые заявки/переписка 90 дней, служебные логи 14 дней, резервные копии 30 дней. Автоматического удаления по расписанию в v1 нет; ответственному назначается регулярная проверка.

Удаление одной заявки сначала показывает preview, затем требует точного reference. Команды выполняются offline после остановки приёма, worker и расписаний:

```powershell
.\.venv\Scripts\python.exe -m app.retention --lead-id <UUID>
.\.venv\Scripts\python.exe -m app.retention --lead-id <UUID> --confirm-reference <REFERENCE>
```

Активные задания и `sending` блокируют удаление. Несопоставленные входящие письма, почтовый сервер, Telegram, данные AI-провайдера и старые backups требуют отдельной обработки. Запись opt-out сохраняется отдельно; её срок согласуется с владельцем данных. Удаление заявки не должно снова разрешать сообщения этому адресу.

## Docker Compose — подготовленный, но не подтверждённый путь

**BLOCKED для исполнения здесь:** Docker Engine недоступен. Dockerfile/Compose подготовлены; до контейнерного smoke нельзя объявлять этот путь VERIFIED. Запуск Docker, системные изменения или публичная публикация требуют соответствующего разрешения. Следующие команды предназначены для согласованного окружения с работающим Engine.

Создание отдельного demo-окружения и workflow с адресом backend внутри сети:

```powershell
.\.venv\Scripts\python.exe scripts/init-compose-env.py
$env:BUILD_BACKEND_URL = 'http://app:8000'
$env:BUILD_WORKFLOW_OUTPUT = '.local/compose-workflows'
node n8n/build-workflows.mjs
Remove-Item Env:BUILD_BACKEND_URL
Remove-Item Env:BUILD_WORKFLOW_OUTPUT
docker compose --env-file .env.compose config --quiet
```

Генератор секретов отказывается перезаписывать существующую `.env.compose`. Статическая проверка не печатает секреты. Compose публикует только loopback UI `8080` и редактор n8n `5681`; локальный npm n8n нужно предварительно остановить из-за совпадающего host-порта.

```powershell
.\scripts\stop-n8n.ps1
docker compose --env-file .env.compose up --build -d postgres n8n app proxy
```

Не запускать worker до импорта credentials и активации workflow. Внутри Compose роли приложения/n8n раздельны, PostgreSQL не публикуется на host-порт. Настройка публичного HTTPS в этом demo Compose не выполнена.

Credentials для контейнера **не переносятся** из локального npm n8n. Создайте временный JSON вне репозитория с двумя объектами следующей формы, подставляя токены из `.env.compose` в локальном редакторе, без вывода в терминал или чат:

```json
[
  {
    "id": "aiLeadInternalAuth",
    "name": "AI Lead Internal API",
    "type": "httpHeaderAuth",
    "data": {"name": "X-Internal-Token", "value": "INTERNAL_TOKEN_FROM_ENV_COMPOSE"}
  },
  {
    "id": "aiLeadWebhookAuth",
    "name": "AI Lead Dispatch Webhook",
    "type": "httpHeaderAuth",
    "data": {"name": "X-Webhook-Token", "value": "N8N_WEBHOOK_TOKEN_FROM_ENV_COMPOSE"}
  }
]
```

Штатные CLI-команды ниже подтверждены на установленном n8n 2.40.7; их контейнерное выполнение пока не проверено:

```powershell
$credentialFile = Join-Path $env:LOCALAPPDATA 'AILeadAutomationPro\compose-credentials.json'
docker compose --env-file .env.compose cp $credentialFile n8n:/tmp/ai-lead-credentials.json
docker compose --env-file .env.compose exec -T n8n n8n import:credentials --input=/tmp/ai-lead-credentials.json
docker compose --env-file .env.compose exec -T n8n n8n import:workflow --separate --input=/imports
docker compose --env-file .env.compose exec -T n8n n8n publish:workflow --id=aiLeadProcessing
docker compose --env-file .env.compose exec -T n8n n8n publish:workflow --id=aiLeadCommunication
docker compose --env-file .env.compose exec -T n8n n8n publish:workflow --id=aiLeadMailSync
docker compose --env-file .env.compose exec -T n8n n8n publish:workflow --id=aiLeadFollowupCheck
docker compose --env-file .env.compose exec -T n8n rm /tmp/ai-lead-credentials.json
Remove-Item -LiteralPath $credentialFile
docker compose --env-file .env.compose restart n8n
```

Удалить временные credential-файлы и при ошибке импорта; до удаления убедиться, что это именно созданные для этого шага файлы. Создать owner в локальном редакторе n8n и проверить все четыре триггера, включая оба расписания. Затем создать demo-оператора, данные и запустить worker:

```powershell
docker compose --env-file .env.compose exec app python -m app.cli create-operator --email operator@example.com
docker compose --env-file .env.compose exec -T app python -m app.cli seed-demo
docker compose --env-file .env.compose up -d worker
```

Проверить полный demo-путь через `http://127.0.0.1:8080`. Остановить Compose можно через `docker compose --env-file .env.compose down`; не добавлять `-v`, если данные нужно сохранить. Эта поставка не создаёт публичный сервис и не является готовой live-конфигурацией.

## Подготовка клиента

До внесения реальных данных согласовать компанию, услуги, критерии квалификации, privacy-текст, сроки хранения, список операторов, mailbox, шаблоны допустимых ответов и порядок работы с opt-out. Конфигурация компании имеет версию; пересмотр оценок старых заявок выполняется явно.

Для отдельного live-развёртывания нужны своя БД/роль с паролем, отдельный n8n, HTTPS и secure cookies, отдельные служебные токены, защищённое хранение секретов, резервирование и проверка восстановления. Приложение проверяет mode развёртывания в БД; переключение demo-БД в live не является допустимой миграцией. Запуск оплачиваемых ресурсов, публичный деплой, работа с реальными данными и внешние отправки отдельно согласуются.

| Интеграция | Что проверить до live |
|---|---|
| OpenAI | Доступ к выбранной модели, строгая схема, refusal/timeout, evidence и размеченные RU/EN-примеры; бюджет и лимит параллелизма |
| Telegram | Согласованные bot/chat, одно служебное уведомление на HOT-событие, ошибки и неопределённый результат; только после разрешения тестовой отправки |
| SMTP | TLS/учётная запись/From, контролируемый получатель, явное одобрение версии, отказ/таймаут и `delivery_unknown` |
| IMAP | Папка/UIDVALIDITY/курсоры, повторная загрузка, threading, автоответы, несопоставленные письма и свежесть sync |
| n8n | Production webhooks, два различных credential, четыре activated triggers, восстановление после остановки |

Фактическое принятие SMTP-провайдером не доказывает доставку или прочтение. Даже свежий IMAP не делает получение ответа и отправку SMTP одной атомарной операцией. Оператору нужно показывать эти состояния без обещания exactly-once.

Эксплуатационные расходы складываются из инфраструктуры, резервных копий, домена, почты, AI usage и сопровождения. В приложении можно задать подтверждённые тарифы `AI_INPUT_PRICE_PER_MILLION`, `AI_OUTPUT_PRICE_PER_MILLION`, `AI_PRICE_MODEL`, `AI_PRICE_SOURCE`, `AI_PRICE_AS_OF` вместе с валютой `AI_PRICE_CURRENCY`. Это оценка на основе сохранённого usage, не счёт провайдера. При неизвестном usage или другой модели стоимость остаётся неизвестной; не подставлять ноль. Доступ к Codex не используется как API-доступ приложения.

Перед передачей клиенту также проверить лицензии выбранного способа поставки n8n и зависимостей, владельца backup/удалений и порядок ручной сверки неопределённых отправок. Условия размещения и обработки данных определяются для конкретного клиента; этот документ не обещает соответствия всем юрисдикциям.

По [официальному разъяснению n8n](https://support.n8n.io/article/can-i-use-your-license-for-my-use-case), проверенному 26.09.2026, помощь с внутренним экземпляром самого клиента рассматривается как консалтинг. Размещение клиентских workflows/credentials в собственном экземпляре исполнителя и встраивание n8n в перепродаваемый продукт имеют другие лицензионные условия. Поэтому исходная модель пилота — отдельное окружение клиента; конкретные права зависят от его сценария и текущих условий n8n. Не считать этот проект разрешением перепродавать доступ к n8n. Лицензия на собственный код проекта пока не назначена: перед внешним распространением её выбирает владелец.

## Состав ограниченного пилота

Подходящий первый клиент — небольшое B2B-агентство с согласованными услугами и оператором, который ежедневно проверяет черновики. Пилот включает один конфиг компании, одну форму, одного AI-провайдера, один SMTP/IMAP-ящик, Telegram для менеджера, обучение оператора и проверку восстановления. Чувствительные решения о найме, здоровье, кредитовании и автоматические переговоры в этот объём не входят.

До начала письменно определить разрешённый объём обращений, срок пилота, ответственного за одобрение и данные, окно поддержки и порядок эскалации. Приёмка: корректность извлечённых фактов на согласованной выборке, отсутствие отправок без одобрения, понятное восстановление ошибок и рабочее входящее сопоставление. Коммерческий результат измеряет клиент; гарантий продаж нет.

Сопровождение должно отдельно определить обновление зависимостей, исправление дефектов ядра, настройку новых правил и реагирование на сбои сторонних сервисов. Доступность провайдера, попадание письма во входящие, изменения его API и круглосуточная поддержка не возникают автоматически из поставки исходников. Оплачиваемые сервисы оформляются владельцем согласованного окружения.

## Controlled и персонализированный draft

Отдельные ports/DBs, hidden-key flow, запрет повторов и точная команда: [CONTROLLED_MODE.md](CONTROLLED_MODE.md). Поставка/обновления и rollback: [DEPLOYMENT.md](DEPLOYMENT.md). Клиентская приёмка: [PILOT_CHECKLIST.md](PILOT_CHECKLIST.md). Основной demo конфиг не переключён в live.

Новые бизнес-настройки имеют defaults и читаются BusinessConfig: `draft.prompt_version`, `draft.max_output_tokens`, `draft.timeout_seconds`, `draft.business_instructions`, `draft.call_to_action_ru/en`, `notifications.hot_enabled`. Два существующих YAML продолжают проходить validation без изменений. `REAL_DRAFT_ENABLED` — process setting, не публичная настройка и не UI toggle. В demo/test запрещена; в controlled smoke false. Изменение production config требует проверки и restart собственных API/worker, старые jobs сохраняют snapshot.

Draft errors не включают fake fallback. Usage/резерв учитывают analysis и draft; missing usage сохраняется неизвестным. Одобрение остаётся отдельным точным действием оператора. Один real draft VERIFIED controlled ($0.000626), без approval/send; новый subject-branding prompt lead-draft-2 проверен только бесплатно. Дополнительные live проверки запрещены без отдельного разрешения. Перед реальными коммуникациями нужны согласованные credentials/test recipients и разрешённый пилот.
