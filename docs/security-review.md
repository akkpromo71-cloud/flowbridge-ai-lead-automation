# Проверка безопасности и корректности backend

Проверка выполнена по исходному коду и бесплатным тестам на синтетических данных.
Это инженерная проверка конкретной версии, не аудит инфраструктуры клиента и
не подтверждение работоспособности платных или почтовых live-сервисов.

## Найденные и исправленные дефекты

| Дефект | Последствие до исправления | Исправление и доказательство |
|---|---|---|
| Старое задание отправки изменяло состояние общей карточки сообщения | После редактирования и одобрения v2 отказ старого v1 переводил уже одобренную v2 в failed | `communication.message_failure` блокирует Lead/Message и проверяет ключ точной текущей версии. Регрессия подтверждает отказ v1 и одну успешную fake-отправку v2 |
| Восстановление старого send-job не проверяло версию | Истечение lease v1 могло пометить начатую отправку v2 как delivery_unknown | `jobs._reconcile_recovery` проверяет привязку задания к текущей версии перед изменением Message |
| Исчерпание доставок или lease не отражалось в заявке | Job уже failed, карточка бесконечно показывала pending/processing | Восстановление и terminal webhook failure согласуют видимое состояние Lead. Успешный анализ не стирается из-за сбоя более позднего draft/finish |
| Повторное одобрение версии с завершившимся ошибкой send-job создавало фиктивную очередь | Message становилось queued, но уникальный dedup-key не позволял создать новое задание | `admin.decision` требует новую версию после failed/rejected/терминального прежнего задания |
| Ручная проверка follow-up повторно использовала старую версию | Новое одобрение могло ссылаться на старое завершённое задание либо неоднозначную отправку | Проверка создаёт новую revision без одобрения. Для sending/provider_accepted/delivery_unknown/cancelled возобновление запрещено |
| Неудачная подготовка follow-up до появления черновика не восстанавливалась после ручной проверки | Цикл scheduled → конфликт уникальности → needs_review | Явная ручная проверка повторно ставит то же draft-only задание; автоматического повторного внешнего сообщения нет |
| Дневной AI-бюджет использовал время создания шага | Захват до полуночи и резерв после неё учитывались в предыдущем UTC-дне | `JobStep.reserved_at` фиксируется при резерве. Дневной лимит и техническая аналитика привязаны к нему; известный usage связывается с соответствующим завершённым шагом, а не днём завершения анализа |
| Транспортные и access-логи могли содержать секрет или контакт | HTTPX на INFO печатает URL Telegram с bot token, а uvicorn.access — поисковый email в query string | `logging_privacy.configure_private_logging` отключает httpx/httpcore/uvicorn.access при создании API и запуске worker. Проверка настоящего HTTPX-клиента через MockTransport не обнаруживает синтетический token в INFO-логе; метаданные ошибок приложения остаются |
| CLI и worker не проверяли маркер режима БД до изменений | При ошибочном DATABASE_URL demo-процесс мог создать синтетические заявки/оператора либо захватить live-задания | Общий `deployment.ensure_database_mode` атомарно создаёт маркер только при его отсутствии и проверяет совпадение. API, worker и CLI создания данных вызывают его до изменений. Проверены шесть точек входа и конкурентный bootstrap одинаковых/разных режимов |
| Неоднозначное входящее письмо не блокировало ранее одобренный follow-up после свежей синхронизации | Синхронизация могла скрыть сохранённую необходимость ручного разбора | `blocked_reason` учитывает needs_review. Регрессия: unmatched → fresh sync → финальный gate всё равно отказывает |
| Ссылки анализа и версии проверяли существование, но не владельца | Прямое некорректное изменение БД могло связать анализ с чужой заявкой или версию с чужим сообщением | Составные отложенные FK проверяют владельцев. Тесты подтверждают отказ и успешное каскадное удаление собственного графа |

В предыдущих проходах также исправлены порядок сохранения версии перед её
указателем, повторная подготовка follow-up при конфликте уникальности и
устаревшая попытка анализа, способная вернуть завершённую карточку в processing.

## Проверенные свойства

- Одобрение требуется для текущих subject/body/recipient. Редактирование создаёт
  новую версию и отменяет старое разрешение. Нет публичного или служебного
  маршрута, который меняет approval в обход оператора.
- Конкурентный callback одного шага получает одного владельца; другой получает
  `409`. Generation/token/lease проверяются перед применением результата.
  Поздний ACK не откатывает running/succeeded в dispatched.
- Незавершённые send/notify с истёкшим lease считаются неопределёнными.
  `delivery_unknown` не переводится в повторную отправку обычным approve/review.
- Opt-out, остановка, закрытие, сохранённый ответ и needs_review проверяются
  в финальной проверке follow-up. Ручная проверка не восстанавливает одобрение.
- При AI-вызове нет открытой DB-транзакции. При IMAP удерживается отдельная
  advisory-lock сессия в AUTOCOMMIT; тест проверяет отсутствие idle-in-transaction
  непосредственно на границе имитированного сетевого вызова.
- Demo/test отвергают OpenAI/Telegram/SMTP/IMAP live-секреты и реальные отправки.
  Публичное demo только для чтения; кабинет и внутренний API требуют авторизации.
- Live-конфигурация требует HTTPS, Secure-cookie и разные сильные служебные токены.
- Unknown AI usage сохраняется неизвестным; бюджет резервируется консервативно.
  Цена не выводится как известная при неизвестном usage или отсутствии тарифа.

Основные регрессии: `backend/tests/test_security_review.py`, `test_jobs.py`,
`test_constraints.py`, `test_processing.py`, `test_communications.py`, `test_admin.py`,
`test_metrics.py`, `test_logging_privacy.py`, `test_demo_reply.py`. Связанные операции находятся в `backend/app/jobs.py`,
`processing.py`, `communication.py`, `admin.py` и `security.py`.

## Остающиеся границы

- SMTP и IMAP не участвуют в общей транзакции. Ответ, пришедший после финальной
  проверки, может пересечься с уже начатой отправкой. `provider_accepted` не
  означает доставку или прочтение; exactly-once у провайдера не гарантируется.
- Lease блокирует применение старого результата, но не отменяет уже начатый
  внешний запрос. Неопределённый результат требует сверки человеком.
- Неизменяемость старых MessageVersion обеспечивают прикладные операции.
  Суперпользователь БД технически может выполнить прямой UPDATE: запрещающего
  триггера нет. Доступ к БД и секретам должен оставаться ограниченным.
- Строгая схема и evidence не доказывают полную семантическую точность модели.
  30 размеченных примеров на конфиг проверяют правила/fake; live evaluation
  выбранной модели требует отдельного разрешённого запуска.
- Тесты SMTP/IMAP используют контролируемые имитации. TLS, права реального ящика,
  deliverability, DNS и действия провайдера требуют отдельной эксплуатационной проверки.
- Внешняя публикация, TLS/proxy-настройки, сроки хранения, восстановление резервных
  копий и доступы клиента проверяются до пилота. Этот файл не заменяет эти проверки.

## Проход завершения, 2026-09-28

Добавлен отдельный controlled mode с физической DB fence, loopback-only URL, запретом Telegram/SMTP/IMAP credentials и внешних отправок. Hidden-key launcher передаёт ключ только в память API, worker и browser получают allowlist без него. Один положительный AI reservation и GuardedTransport(limit=1, SDK/HTTP retries=0) ограничивают разрешённый smoke. Test `test_controlled_configuration_does_not_bypass_demo_or_live` проверяет запреты; `test_controlled_ai_one_attempt_even_on_failure` и HTTP 429 MockTransport подтверждают отсутствие второй попытки.

Draft adapter имеет только subject/body, без tools/recipient/send/approval. Генерация закрывает DB-транзакцию до сети, сохраняет immutable provenance, не создаёт Approval. Новые версии оператора сохраняют ссылку на первоначальную, а прежнее approval очищается. Реальный SDK-контракт проверен MockTransport, **не live качеством**. Список leads больше не делает Analysis SELECT для каждой строки; 350 synthetic rows подтверждают одинаковое число queries для страниц 5 и 100.

Журналирование production не расширялось до raw PII/provider dumps. Model output хранится только в protected MessageVersion как прикладные данные, не в routine logs. В evaluator/controlled отчёте только synthetic fixture, validated facts/метаданные и safe diagnostic, без auth headers/raw provider text. Stored data всё равно требует приватной БД, retention и backup policy.

Проверка существующих auth/CSRF/Origin/expiry/internal token/rate limits/XSS/request limits входит в общий backend/browser suite. CSV export отсутствует: CSV injection не применима. Arbitrary URL-fetching продукта нет. Внешний pentest не проводился. Deployment HTTPS/conf доступность пока не VERIFIED на сервере клиента. Итоговые counts и команды — FINAL_PROJECT_REPORT.md.
